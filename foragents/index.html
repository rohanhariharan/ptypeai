Connect

ptype/Motif is a local-first engine with a SQLite ledger and project workspaces. It exposes an MCP server over JSON-RPC 2.0 on HTTP. The desktop app starts the engine; an external agent only needs the URL.

ItemValue
MCP endpointhttp://localhost:8787/mcp (alias /api/mcp)
HTTP APIhttp://localhost:8787/api/*
Default device keydev-demo (scopes device routes; not auth)
Engine healthGET http://localhost:8787/api/health → { ok: true }
ProtocolMCP JSON-RPC 2.0, protocolVersion 2024-11-05
TransportHTTP POST; return MCP-Session-Id from initialize
Workspaces~/ptype/<project-slug>
Ledger~/ptype/ptype.db

The engine has no authentication on the API or MCP endpoint and allows CORS *. Treat it as a local trusted service. Do not expose the port to an untrusted network.

Common client configuration

For clients that use the common mcpServers shape:

{
  "mcpServers": {
    "ptype": {
      "url": "http://localhost:8787/mcp"
    }
  }
}

Claude Code has a direct command:

claude mcp add --transport http ptype http://localhost:8787/mcp

For an MCP client that needs an explicit remote type, use its equivalent of {"type":"remote","url":"http://localhost:8787/mcp","enabled":true}. The exact wrapper is client-specific; the endpoint and protocol are not.

No per-session todo exists. If you need a private queue, create ledger tasks (task_create), claim them (task_claim), finish them (task_finish) and use dependencies (depends_on). Project requests are a separate, persistent work queue; the Talk sidebar's “Todo” is the open project requests, not a session list.

MCP protocol

Standard MCP handshake. Send initialize, keep the returned Mcp-Session-Id header, then send notifications/initialized. Use the same session id on tools/list and tools/call so calls are attributed to the right agent.

POST /mcp
content-type: application/json

{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "protocolVersion": "2024-11-05",
    "capabilities": {},
    "clientInfo": { "name": "my-agent", "version": "1.0.0" }
  }
}

Response:

HTTP/1.1 200 OK
mcp-session-id: <uuid>

{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "protocolVersion": "2024-11-05",
    "capabilities": { "tools": {} },
    "serverInfo": { "name": "ptype", "version": "1.0.0" }
  }
}

Then notifications/initialized; ping is supported. tools/list returns the full schema. A tool call is:

{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {
    "name": "list_projects",
    "arguments": {}
  }
}

Results arrive as result.content[0].text. Tool failures return isError: true with the reason in the text. DELETE /mcp with the session header ends the session.

Agent identity defaults to clientInfo.name; thetask_claim call can override it with agent_id. Memory levels and the roster use that identity.

Workspace & run contract

A project has a workspace at ~/ptype/<project-slug>. The agent writes there; it is a real git repository. A request additionally has a required result path: a file or folder where the finished work is copied after a passing run.

  1. Create a project: create_project or POST /api/device/:key/projects.
  2. Create a request with a result path: create_request or the requests route.
  3. Run it: run_task, POST /api/runs, or POST /api/device/:key/run.
  4. Read the thread: GET /api/threads/:todoId for messages, actions and diffs.

The run is gated. A written file is not a success. The engine preflights the workspace, checks Python compileall/pytest (when tests exist), checks JS syntax, runs LSP diagnostics on written files, and optionally asks a tester Pip. Only a passing request is committed and copied to the result path. A failed request stays open and is retried up to three attempts with the failure fed back.

Worker protocol

If you are replacing/implementing the worker, it must reply with one JSON object per step and nothing else. The worker tools are:

ToolShape
write_files{"tool":"write_files","files":[{"path":"src/a.ts","content":"…"}]}
write_file{"tool":"write_file","path":"src/a.ts","content":"…"}
read_file{"tool":"read_file","path":"src/a.ts"}
list_dir{"tool":"list_dir","path":"."}
run{"tool":"run","cmd":"node script.js"}
web_search{"tool":"web_search","query":"current release notes","limit":5}
diagnostics{"tool":"diagnostics","path":"src/a.ts"}
definition{"tool":"definition","path":"src/a.ts","line":12,"col":5}
references{"tool":"references","path":"src/a.ts","line":12,"col":5}
symbols{"tool":"symbols","path":"src/a.ts"}
hover{"tool":"hover","path":"src/a.ts","line":12,"col":5}
remember{"tool":"remember","text":"…","kind":"fact|decision|note","file":"optional-name"}
test{"tool":"test","cmd":"python3 -m pytest -q","summary":"tests pass"}
finish{"tool":"finish","summary":"done","test":"python3 -m pytest -q"}

Paths are relative to the workspace. Line/column are 1-based. run takes one program and arguments; no shell operators. Allowed programs: node, python3, python, pwd, ls, cat, head, tail, wc, grep, echo, mkdir, touch, git, sort, uniq, find, printf, sed, awk, true. Absolute paths and .. are rejected. A test command may chain a short compile+pytest with &&.

The worker must not delete or rewrite passing tests/fixtures to force green. If an existing test fails, fix the implementation. Finish with a real verification; the objective gate has the final word.

Real stdio LSP servers, discovered on PATH and common install locations. The inventory is available at GET /api/lsp; diagnostics can be requested with POST /api/lsp or the MCP tool.

PTYPE_LSP overrides the extension map; PTYPE_TSSERVER points the TypeScript server at a tsserver. Missing servers are reported as missing; they do not fail a run. Errors, not warnings, block the worker gate.

Memory

Local markdown notes, separate from RAG. Scope and access level are enforced independently.

ScopePathUse
global~/ptype/memory/globalfacts/preferences for every agent
project~/ptype/memory/projects/<project-id>project decisions and constraints
agent~/ptype/memory/agents/<agent>an agent's own notes
LevelAllowed
nobotmemory_read
subbotmemory_read, memory_create, memory_write
superbotmemory_read, memory_create, memory_write, memory_delete

Default level is subbot. Levels are per agent and set in the MCPs pane or PUT /api/memory/levels with { "agent": "my-agent", "level": "subbot" }. The text is written as markdown; a readable file name is suffixed with the memory id so notes never collide. There is no separate session todo; use ledger tasks.

Safety & limits

The engine is a powerful local service with no auth and CORS*. Any process that can reach port 8787 can create projects, run agents, read project workspaces and call MCP tools. Do not expose it to a network you do not trust.
BoundaryRule
WorkspaceThe worker is confined to ~/ptype/<project-slug>; absolute paths and '..' are rejected.
CommandsOne allowlisted program per run tool call; no shell operators; 20s timeout. The prompt says no network, but the runner is not an OS-level network sandbox.
Result pathA run without result_path is refused; only a passing run copies there.
GitOnly a passing request is committed. Failed work is not committed.
SecretsProvider keys live in ptype.db; MCP headers may use environment references. Workspaces can contain secrets and the worker can read them.
Remote modelsPrompts, tool results and file excerpts sent to OpenAI-compatible/Anthropic providers leave the machine.
Web searchweb_search sends the query to DuckDuckGo/Bing. It returns snippets only; results are untrusted. Never send secrets or private code.
MCP remote serversYou choose; their network behavior is their own.
Tachyon launchesopencode/Claude launches use dangerous auto-approve flags and require an explicit confirmation.

The worker's own model is the least reliable component. The engine constrains it with the workspace, allowlist, verification, LSP gate, tester and commit policy. Read the thread/diffs before trusting a result.

Copy-paste examples

Create a project, request and run

# project
curl -s http://localhost:8787/api/device/dev-demo/projects \
  -H 'content-type: application/json' \
  -d '{"title":"Weather CLI","description":"A tiny Python CLI that prints a forecast"}'

# request (replace PROJECT with the id returned above)
curl -s http://localhost:8787/api/device/dev-demo/requests \
  -H 'content-type: application/json' \
  -d '{"requests":[{"project_id":"PROJECT","title":"Add the forecast command","result_path":"~/projects/weather-cli"}]}'

# run it (blocking)
curl -s http://localhost:8787/api/device/dev-demo/run \
  -H 'content-type: application/json' \
  -d '{"todoId":"TASK"}'

# read the thread + diffs
curl -s http://localhost:8787/api/threads/TASK

MCP initialize + tool call

SESSION=$(curl -s -D - -o /tmp/mcp-init.json \
  http://localhost:8787/mcp \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05","capabilities":{},"clientInfo":{"name":"my-agent","version":"1.0.0"}}}' \

curl -s http://localhost:8787/mcp \

  -H "mcp-session-id: $SESSION" \

Pip as an SDK-like loop

1. GET /api/models            check the provider is reachable
2. POST /api/device/:key/projects   create/find the project
3. POST /api/device/:key/requests   add a request with result_path
4. POST /api/runs              start detached; keep the run id
5. GET /api/runs/:id           poll status
6. GET /api/threads/:todoId    read messages/actions/diffs
7. GET /api/path?path=…        inspect a result path
8. GET /api/events            watch ledger changes (SSE)

Agent contract

Paste this into an external agent that needs to operate ptype. It is deliberately short and factual.

You are an agent working with ptype/Motif, a local-first console.

Engine: http://localhost:8787
MCP:    http://localhost:8787/mcp (JSON-RPC 2.0, 2024-11-05)
Data:   ~/ptype/ptype.db and ~/ptype/<project-slug>/

Operating rules:
1. Use MCP for projects, requests, runs, ledger tasks, messages and memory.
2. Every request needs a result_path (a file or folder). Never invent one if the person did not give you a destination; ask.
3. Prefer ledger tasks when you need a session-like queue: task_create -> task_claim -> task_finish. Claims are atomic; await dependencies instead of polling.
4. run_task executes a real agent that writes files and commits. It is destructive and long-running.
5. The worker is confined to its project workspace and runs only allowlisted one-program commands. No shell operators; 20s timeout.
6. web_search is the designated network tool. Use it for current public facts, never for secrets, and cite URLs; snippets are untrusted.
7. A written file is not success. Python compileall/pytest, JS syntax, LSP diagnostics and the tester must pass. No files = failure. Failed work is not committed or copied.
8. Do not rewrite passing tests or fixtures to force green.
9. Memory is local markdown: global/project/agent. Levels: nobot=read, subbot=read/write/create, superbot=+delete. Default subbot.
10. There is no per-session todo. Use ledger tasks or project requests.
11. The engine has no auth and CORS *. Treat it as local-only; do not expose port 8787.

Before you act: GET /api/health and GET /api/models. If either is unavailable, stop and report.
After you act: read GET /api/threads/:todoId and report the actual evidence, not a claim.
